## 1. Page Purpose (step 10)

**Wording proposé (09/25) :**
> Horeb ouvre le **board Kanban global (S-05)** depuis la liste plate de tâches (05.3) et voit ses tâches **trées par statut** (5 colonnes : à faire / en cours / bloqué / terminé / annulé, ADR §2.2 ; pack 05 §4.3.3) — **le Kanban global est transverses, pas par projet** (le Kanban par projet vit dans `projets-detail` §4.3.2 ; le board global = le **tri** par statut). Elle **glisse sa tâche nocturne** de la colonne « à faire » vers la colonne « en cours » — **le drag est une écriture locale (AD-7)** : le mouvement de card se fait **immédiatement et hors-ligne** (le mouvement = mutation queue, pack 03 §5.5 ; la **sync** se fait au retour du réseau, pack 03 §5.5 re-sync) ; seul le **scan** (extraction de tâches depuis des documents) est désactivé en offline (pack §4.3.3). La page ne fait qu'une seule chose : **triér les tâches par statut et rendre le move de statut actionnable en 1 geste** (le drag = le **move** de statut, pas un « drop » vers une 6ᵉ colonne inexistante — l'état `annulé` est une **colonne séparée**, jamais un « trash » déguisé).

## 3. Mental State (step 12)

**Contexte de la page** : 23 h 05, chambre, Pixel 4a, thème Nocturne, réseau 3G Bénin instable (AD-7, offline = état premier). Horeb vient de consulter sa **liste plate de tâches** (05.3) : sa **tâche nocturne** n'a pas encore de statut défini (elle est « à faire » mais non positionnée). Elle ouvre le **board Kanban global** pour **la glisser vers « en cours »** — fermer proprement sa journée, sans ajouter de widget ni attendre le réseau.

| Dimension | Contenu |
|---|---|
| **Trigger** (ce qui la pousse) | Le pas 05.3 (liste plate S-32) l'a laissée avec une **tâche nocturne sans statut** — elle veut **la positionner** sur le board pour **commencer** réellement (« en cours » = le cycle de productivité s'enclenche, ADR §2) et **boucler proprement la routine du soir** (scénario 05 Q4 ; trigger-map §2 Envie ① Focus) |

## 4. Desired Outcome (step 13)

### Business Goal
**Régularité mesurée (fidélisation) : le cycle de productivité est concret et visible** — le board Kanban global est la **preuve** que la tâche nocturne **a été positionnée** (drag « à faire » → « en cours », un **move de statut** traçable, ADR §2.2) ; chaque move = une **preuve d'action** (pas un compteur de tâches) qui alimente la transformation réelle continue (BG-PRIMARY, scénario 05 Q2 ; ADR §18.2 transformation dans le temps ; trigger-map §1 Primary ; ADR §2 cycle de productivité). Source : strategic-chains Chaîne 05 Q8 passo 4 ; `master-feature-catalog` (tâches par statut, ADR §2.2).

### User Goal
**Glisser sa tâche nocturne de « à faire » vers « en cours » en 1 geste, hors-ligne** — le mouvement est **local et immédiat** (AD-7, pack 03 §5.5 : mutation queue, sync au retour) ; Horeb **voit** que sa tâche est maintenant « en cours » (le `Badge` de statut s'actualise sans cloud) et **boucle proprement** la routine du soir — elle ouvre ensuite l'overlay de détail (05.5, S-24) pour lire les sous-tâches. Source : scénario 05 Q4 (Hope), Q8 passo 4 ; pack 05 §4.3.3 (drag local possible offline) ; ADR §2.2 statuts.

Seule l'opération **scan** (extraction de tâches depuis des documents) est **désactivée** en offline (pack §4.3.3). Le drag **n'exige pas le réseau** — c'est le cœur du AD-7 pour cette surface.

- **Transition Card → `taches-detail`** (S-24, 05.5) : le détail **lourd** s'ouvre en **`BottomSheet full` par-dessus le board** (pack §4.3.3, règle de non-surprise : le Kanban **reste** visible en arrière-plan, on revient au board, pas à une liste).

Le **FAB chat S-29** (OQ-4) est **masqué** ici (le 5ᵉ tab BottomNav est l'entrée principale sur les écrans à BottomNav) ; le **FAB local « Nouvelle tâche »** et le **FAB chat S-29** sont **distincts** (voir OQ-1 pour le conflit de deux FABs — la proposition est de **ne pas afficher les deux simultanément** sur la même page : le FAB local (Nouvelle tâche) est présent ; le FAB chat (S-29) est masqué, le 5ᵉ tab BottomNav gère l'accès au chat).
- **`KanbanCard`** = une card **compacte** : titre (1 ligne, ≤ 60 caractères) + `Badge` (le **statut** de la card) + `ProgressBar` (le % de complétion si elle a des sous-tâches — pack §4.3.3 DS) — **pas un dashboard, pas un compteur** (trigger-map §6 trap « Surcharge de widgets »).
- **Le drag mobile (540 px, 5 colonnes) est le point NON COUVERT clé** (OQ-1) : le pack §4.3.3 décrit le drag en **general** (desktop : horizontal) ; le **tranchement mobile exact** (drag-and-drop direct vs tap-then-menu « Changer le statut ») n'est **pas dans le corps gelé** — la proposition (voir OQ-1) est le **tap-then-menu** (un **tap long** sur la card → un **`Menu`** « Changer le statut » → 4 options (en cours / bloqué / terminé / annulé) → **1 tap** = le move local AD-7) — **plus fiable** sur 540 px / 30 fps que le drag-and-drop multi-touch, et **cohérent** avec le `Menu` §3.6.4 du pack 05 (le `Menu` filtre de la TopBar est déjà le pattern de choix de statut).
