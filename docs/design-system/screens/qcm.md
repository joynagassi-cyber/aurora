# Écran : qcm — QCM

> Module Learning · Route `/learn/:id` (overlay IonModal sur le tab courant, 02 §6.1 S1/S3, router.tsx) · SSoT 05 §4.8.2 + WDS 01.4 · Statut : détaillé

## §1 Psychologie designer

- **Objectif utilisateur** : **tester** la compréhension — exécuter un QCM séquentiel (une question à la fois, validation avant suivante) généré par l'agent serveur (AD-12/F-09), et analyser les erreurs à la fin (correction + explication séparée, AD-11).
- **Contexte** : mobile, main libre, réseau 3G instable probable ; ouverture depuis `fiches-detail` (§4.7.1) ou `cours-detail` (§4.7.1.2) via le bouton « Tester » ; overlay = l'utilisateur reste dans son flux (pas de navigation destructive). Sessions nocturnes possibles (thème Nocturne par défaut, OQ-16 WDS 01.4).
- **Fréquence** : à chaque session de révision (plusieurs fois par semaine) ; QCM = `ProgressEvidence` (doc §18.3) — le résultat est **persisté** (AD-7 local, synchronisé) et alimente `progress-dashboard` (§4.5.2).
- **État émotionnel cible** : concentration (épreuve cognitive), confiance (séquencement clair, progression fine visible), calme (pas de frustration si échec : correction lisible, retry disponible), motivation (score visible, « relancer le QCM »).
- **Erreur la plus probable** : cloud indisponible pendant la **génération** du QCM (AD-4, agent serveur AD-12/F-09) → `Callout danger` + CTA « Réessayer » ; le QCM **n'est pas** exécutable hors-ligne (pas de support local, 05 §4.8.2).
- **Ce que l'écran RÉSOUT** : surface d'exécution séquentielle du QCM (3 zones fixes : progression, question courante, actions) + écran de résultat (score + correction/erreur par question) + actions flottantes (relancer / réviser les fiches des erreurs). La **génération** est différée au serveur (AD-12), l'**exécution** est locale (AD-7) — le QCM existant reste lisible hors-ligne.

## §2 Contexte fonctionnel

- **Entrée** : CTA « Tester » depuis `fiches-detail` (§4.7.1) ou `cours-detail` (§4.7.1.2) ; deep link `/learn/:id` (push notification, automatisation, S-31 parcours Learning) ; retour natif depuis `/progress` si l'utilisateur revient en arrière (invariant S6.2).
- **Overlay IonModal `/learn/:id`** (router.tsx detail-over-tab rule 02 §6.1 S1/S3) : le tab courant reste sous l'overlay (pas de navigation destructive).
- **Data** : QCM = **génération à la volée** par l'agent serveur (AD-12/F-09, kernel `Plan → Retrieve → Tools → Verify`) ; le QCM est un `ProgressEvidence` (doc §18.3, AD-9/F-07) — **jamais** créé directement par Learning (AD-2/F-07 : les événements Learning **alimentent** le QCM, seul Progress émet `ProgressEvidenceCreated` pour le QCM).
- **Async** : génération du QCM = **flux serveur** (AD-12) → killed possible sur ce flux ; exécution du QCM existant = **locale** (AD-7, SQLite) → lecture hors-ligne OK. Pas de mirror local pour la génération (AD-7 « offline = état premier », mais le module est serveur-only pour la génération, AD-12).
- **Saisie** : `RadioButton` (groupes exclusifs, 05 §3.2) — une seule sélection par question (pas `MultiSelect`, 05 §4.8.2 : « l'état de la question est **un seul** choix »). Pas de `TextField` (pas de saisie libre dans un QCM, S3 l.137 ion-item forms interdit).
- **Séquencement** : le QCM est **séquentiel** (une question à la fois, validation avant suivante, 05 §4.8.2 : « la question suivante ne révèle pas la réponse tant que la précédente n'est pas validée — le QCM est séquentiel, pas un formulaire libre »). Pas de saut libre (pas de « question 5 » au milieu du QCM).

## §4 États (matrice complète AD-13 / 05 §3.7 l.1244–1309)

### (a) 6 états S6 par élément async (ui-libraries §6 l.174–187)

- **loading** (génération du QCM en cours, AD-12/F-09, ~5-15s pour un QCM de 10 questions) : Zone contenu = Skeleton de la liste des questions (shape final, 05 §3.3) + ProgressRing 48px (05 §3.3) au centre ; tokens = --aurora-skeleton ; texte exact = « Génération du QCM… » (court, car serveur AD-12) ; CTA = aucun (pas de retry pendant le loading) ; **entrée** = fade 200ms easeOut (PAGE_TRANSITION, ssootCode motionRefs motion.tsx @aurora/ui) ; **sortie** = skeleton → contenu partiel crossfade 200ms (pack 02 §7 : si > 300ms, le contenu apparaît partiellement en dessous du Skeleton) ; **pas** de layout animation (S5 l.169).
- **empty** (QCM pas encore généré) : zone contenu vide + CTA primaire « Générer un QCM depuis ce cours » (CTA actionnable, pack 02 §7 : « jamais un bloc vide ») ; tokens = --aurora-bg-subtle + --aurora-text-secondary ; **entrée** = fade 200ms ; **sortie** = tap CTA → flux loading (génération serveur, AD-12) ; si offline → CTA désactivé + explicatif (AD-13 A5).
- **error** (génération a échoué, cloud indisponible AD-4) : Callout danger (« Génération impossible : le cloud est indisponible ») + CTA ghost « Réessayer » (re-soumission, AD-13 A4) ; tokens = --aurora-danger / --aurora-danger-surface ; **entrée** = fade 200ms ; **sortie** = retry OK → flux loading, si fail → retry encore (pas de crash) ; **pas** de Callout qui disparaît (AD-7 : l'erreur est affichée).
- **success** (génération OK, QCM exécuté) : Zone résultat = StatTile KPI du score (05 §3.3) + Callout par question erronée (warning, correction + explication séparée AD-11) ; tokens = --aurora-success / --aurora-success-surface ; **entrée** = fade 200ms ; **sortie** = auto-redirect événementiel vers `/progress` (01.7, 05 §4.8.2 : « le résultat du QCM est un ProgressEvidence persisté (AD-7 local, synchronisé) — la sortie vers progress-dashboard (§4.5.2) conserve le score ») ; **pas** de CTA manuel pour l'auto-redirect (invariant AD-14).
- **offline** (réseau coupé, génération non disponible : module serveur-only AD-12) : Badge offline (header) + Callout info (« Hors-ligne — génération différée. Le QCM existant peut être exécuté. ») ; tokens = --aurora-info (frozen) + --aurora-warning (badge) ; CTA = import/qcm désactivés (pas de CTA serveur) ; **entrée** = fade 200ms ; **sortie** = retour online → refetch (retour au flux loading/success) ; **pas** de CTA d'action (la génération n'est pas actionnable offline, 05 §4.8.2).
- **killed** (flux serveur uniquement, AD-13/G-M2) : Skeleton + « Reconnexion… » ; tokens = --aurora-skeleton (+ --aurora-danger pour le badge d'état) ; CTA = **aucun** (pas de retry, pas de navigation, ssootCode stateRefs ux-states.tsx) ; **entrée** = fade 200ms ; **sortie** = reconnexion OK → re-query → loading/success ; le contenu **local** (AD-7) reste lisible en dessous (pas de crash, pas de perte de contenu local).

## §6 Tokens (discipline AD-17, 05 §2 l.93–346 + ui-libraries S4 l.145–160)

- **Aucune valeur brute** : pas de hex, pas de px de spacing/typo/radius codé en dur — toujours via variables CSS `hsl(var(--aurora-*))` (05 §5.2/5.3, ssootCode tokenRefs aurora.css).
- **Règle bloquante 05 §5.1 (l.2931)** : le thème ne touche **jamais** success/warning/danger/info (frozen semantic tokens) — utiliser uniquement via les variables, pas de redefinition par thème.
- **10 thèmes + 3 presets = comportement par couche** (05 §5.2, ssootCode themeRefs) : pas de valeur par thème (jamais d'override par thème sauf L3 local override = Focus only, OQ-15) ; l'écran ne code **aucune** valeur par thème.
- **focus visible** : le theme owns focus-ring (aurora.json focusTreatment = ring, ssootCode a11yRefs) — pas de gestion manuelle du focus par écran.
- **icônes** : 05 §2.5 (l.287) — lucide (ssootCode paginationRefs Chevrons/MoreHorizontal) ; **pas** de custom SVG decoration (S3 l.141 interdit, ssootCode forbidden).
- **coins** : radius ≤ 8px (S3 l.142 interdit > 8px) ; **élévations** = 05 §2.4 (l.254), pas de box-shadow brut.
- **ProgressBar** : toujours déterminée (le temps est connu, 05 §3.3) — **jamais** `indeterminate` (le glissement = uniquement pour un chargement **réellement** indéterminé, 05 §3.3).

## §8 Pagination

- **Règle unique nommée : shadcn Pagination** (ui-libraries S1 l.37) — **paramètres** : pas de pagination par défaut pour le QCM (une question à la fois, séquentiel, 05 §4.8.2 : « le QCM est séquentiel, pas un formulaire libre »).

## §9 Surfaces flottantes (05 §3.5 l.752–865)
