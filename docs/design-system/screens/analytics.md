## §1 Psychologie designer

- **Objectif utilisateur** : **mesurer** (pas « voir » les statistiques) — l'analytique est le **miroir** de la progression, pas le tableau de bord (doc §2.10 + §18.1, 05 §4.5.2) : l'écran répond aux **5 questions fondamentales** (où en suis-je réellement, qu'est-ce qui s'est réellement amélioré, qu'est-ce qui stagne ou régresse, pourquoi cette évolution, quelle prochaine action produira le plus de progrès utile, doc §18.1) — **structuré par question, pas par widget** (pas un « dashboard de KPIs », AD-14 : l'accueil répond à « Qu'est-ce qui compte maintenant ? », les analytics répondent à « Pourquoi et comment progresser »).
- **Contexte** : mobile, main libre, réseau instable probable ; entrée depuis Home bloc 4 « Progression critique » (§4.1.2, 05 §4.5.2 Transitions) ou depuis focus-mode après une session (§4.4.2) ; 23 h, thème Nocturne (WDS 01.2/01.7), offline = état premier (AD-7). Sessions nocturnes possibles (05 §5.5 presets Nocturne).
- **Fréquence** : à chaque retour sur `/progress` (BottomNav tab 4, OQ-4 close 01.2) ; **re-render événementiel** après une session de preuve (01.7 : l'événement `ProgressEvidenceCreated` AD-9 → ProgressSnapshot alimente le dashboard, ADR §18.6, garde AD-14 : pas de CTA manuel de re-render) — l'écran se **re-peint** automatiquement, l'utilisatrice n'appuie sur rien.
- **État émotionnel cible** : compréhension (l'état, l'évolution **et la cause** du gap — pas un score, 01.2 Mental State), confiance (CTA unique et fixe, AD-14 : « le chemin est le seul chemin »), fierté (état post 01.7 : les 4 preuves affichées, scénario success ✓), calme (pas de frustration si un agrégat est incalculable : Callout warning **signale, ne masque pas**, AD-11, 05 §4.5.2).
- **Erreur la plus probable** : croire que les analytics se mettent à jour **en temps réel** alors que le calcul est un **Job persisté** (AD-8 : « le calcul est un Job persisté, pas synchronisé en temps réel », 05 §4.5.2 état offline) → Callout info « Les agrégats seront recalculés à la reconnexion » (05 §4.5.2) ; ou attendre un seul KPI isolé alors que le design **privilégie la trajectoire et la tendance** (« Privilégier la trajectoire et les tendances plutôt qu'un pourcentage isolé », doc §18.2, 05 §4.5.2 Zones).
- **Ce que l'écran RÉSOUT** : les **5 questions structurées** (doc §18.1) en `ListItem` dépliables, chaque bloc = un bloc de **preuves** (pas d'agrégat isolé, doc §18.2) : `Timeline` (trajectoire temporelle, §3.6.3), `Sparkline` (tendance, §3.6.5), `ChartSpec` G2 (charge planifiée vs réelle, §3.6.1), `StatTile` (taux de réalisation, §3.3), `SkillStateBadge` (progression par compétence, §3.6.11) — + **actions flottantes** : Button ghost « Partager » (export vers Artifact Hub §4.6.1, doc §16 : artefact généré **et** stocké, AD-8 Job persisté, `ArtifactGenerated` AD-9 émis post-upload-R2, F-06) + Button ghost « Ajouter au journal » (doc §2.9 « Journal des décisions importantes » : écrit dans `decisions`, module Productivity, pack 01 §4).

## §2 Contexte fonctionnel

- **Entrées** : Home bloc 4 « Progression critique » (CTA unique et fixe AD-14, §4.1.2) ; BottomNav tab 4 Progress (OQ-4 close 01.2) ; retour natif depuis les surfaces de preuve (invariant S6.2, 01.2 Entry Points) ; **re-render événementiel** `ProgressEvidenceCreated` (AD-9 → ProgressSnapshot, 01.7 : l'entrée primaire de l'état post = l'événement, pas un CTA manuel — garde AD-14, OQ-1 01.7 close option A : CTA fixe « Terminer » = la sortie, l'auto-redirect = l'état post). **Sorties** : `fiches-liste` (réviser la compétence signalée, 05 §4.5.2 Transitions) ; **pas** de sortie vers `progress-dashboard` séparé — « §4.5.2 **est** le dashboard Progress, doc §18.6 : ce n'est pas un écran séparé — c'est lui » (05 §4.5.2) → la route `/progress` de cet écran **est** le dashboard ; `/progress/:id` (router.tsx) ouvre le détail d'une preuve par-dessus le tab courant (02 §6.1 S1/S3, IonModal/IonSlides pattern).
- **Data** : les agrégats (`ProgressTrend`, `ProgressEvent`) sont dans **PostgreSQL** (pack 01 §4, AD-6) — **calculés côté serveur** (05 §4.5.2 États : « les agrégats sont calculés côté serveur ») ; la charge planifiée vs réelle = **lecture** du temps réellement passé (le `FocusTimer` §4.4.2 alimente cette donnée, **AD-7 local** : SQLite, 05 §4.5.2 Objectif) ; les preuves = `ProgressEvidence` (doc §18.3, AD-9 : seul Progress **émet** `ProgressEvidenceCreated`, AD-2/F-07 : les modules alimentent Progress, jamais écriture directe). Le bloc de preuves (question 5, WDS 01.2 OQ-3 close option A : **interne**, pas affiché) = contrat de preuve du moteur, **pas** une question affichée.
- **Async** : **flux serveur** (recalcul des agrégats, AD-8 Job persisté : « le calcul est un Job persisté, pas synchronisé en temps réel », 05 §4.5.2) → `killed` possible (AD-13/G-M2, ssootCode stateRefs ux-states.tsx : killed > offline > query state) ; **lecture locale** (AD-7) → les analytics **existantes** sont consultables offline (les preuves sont dans SQLite, 05 §4.5.2 État offline).
- **Période** : `SegmentedControl` 7 j / 30 j / semestre / année (doc §18.2 « lectures à 7 jours, 30 jours, semestre, année et multi-années », 05 §4.5.2 Zones) ; **retour arrière conserve la période sélectionnée** (store UI pack 02 §3.2, AD-7 persist, 05 §4.5.2 Transitions).
- **Focus Mode** : `/progress` **n'est pas accessible** pendant le focus (le focus bloque les autres surfaces, WDS 01.2/01.7 Variants : « pas de variante Focus : le focus-mode est un état sans chrome, pas une variante de ce dashboard ; si Horeb est en focus, /progress n'est pas accessible, focus-mode §7 »).
