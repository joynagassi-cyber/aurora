# revues-mois — Revues (mois)

Status: SPÉCIFIABLE (OQ: 6) · Module : Productivité · Route : (reviews) · SSoT : 05 §4.5.1 l. 2229-2409 + WDS 06.2 + 05 §3.4 `Pager` l. 737-750 + 05 §3.7 l. 1244-1309 + ui-libraries S1/S3/§6/§9 + master-feature-catalog l. 26 (`productivity.reviews`, offline-capable)

> Le `revues-mois` = le **mode « Mois »** du `Pager` §3.4 (Jour | Semaine | Mois) de l'enveloppe `reviews` (enveloppe #52, inventaire l. 129). Une revue = **une `Card` posée** (pas un `ListItem`) : 5 sections (bilan des tâches / analyse des causes / révision des priorités / plan d'action suivant / journal des décisions), 05 §4.5.1 l. 2264-2310. Ce doc spécifie la zone de contenu en **mode mois** — le même composant `Pager` partagé avec `revues-jour`/`revues-semaine` (05 §4.5.1 l. 2398-2402) ; les zones partagées (TopBar + Pager, BottomNav, 404, offline global) sont référencées vers l'enveloppe. Ce qui **diffère** du mode semaine ici : la période bornée = 1 mois (le volume du `DataTable` bilan **croît** — cf. OQ-2), la **fréquence** est basse (une revue mensuelle, l. 2231-2247), et le `Callout warning` « revue en retard » se calcule **sur la période précédente = le mois dernier** (l. 2323-2330). WDS 06.2 (le scénario `retro-month`, `/progress/retro?range=month`) est la **chaîne de visualisation** qui **précède** la revue mensuelle (le CTA « Voir les actions correctives » de 06.2 pointe vers 06.3, pas vers ce slug) — cf. OQ-1.

## 2. Zones

- **header** : `TopBar` « Revue » (05 §3.4 l. 659-668) + `Pager` §3.4 (Jour | Semaine | Mois, l. 737-750 — **ce slug = le mode Mois**) + `SegmentedControl` « À faire / Faite » (l. 2249-2263 : statut `Review` AD-15 `pending`/`completed`). Le label central du `Pager` affiche **le mois** (« septembre 2026 », `JetBrains Mono` `sm` 600, l. 739-743).
- **content** : une `Review` = une `Card` **posée** (l. 2264-2276), 5 sections **identiques** aux autres échelles (l. 2277-2310) :
  1. `Bilan des tâches` — `DataTable` §3.6.1 (4 colonnes : statut / titre / projet / « pourquoi », l. 2280-2287) — **volume = ~1 mois** (OQ-2 : le seuil < 20 rows est **dépassé**, le SSoT ne tranche pas le wrapper exact)
  2. `Analyse des causes` — `TextArea` + `Badge` d'hypothèse ; 3 `Chip` de causes courantes (charge / fatigue / blocage technique, l. 2299-2310)
  3. `Révision des priorités` — liste `RoutineStep` ordonnée (l. 2288-2291)
  4. `Plan d'action suivant` — liste `RoutineStep` (l. 2292-2294)
  5. `Journal des décisions` — `TextArea` texte libre (l. 2295-2298)
  + `Callout warning` « revue en retard » posé si la revue du **mois précédent** n'a pas été faite (l. 2323-2330)
- **footer** : `BottomNav` (5 items figés, 05 §3.4 l. 670-688)
- **Surfaces flottantes** : `BottomSheet` de **création** de revue (état `empty`, l. 2338-2347 — les 5 sections **pré-remplies** sur 1 mois, l. 2368-2379) ; `Toast` (feedback) ; `Callout info` (reconnexion, killed).
- **Breadcrumb** : **n'existe pas** — la revue est une **feuille** du module Productivité (pas de hiérarchie AD-6).

### 4c. `killed` (tout flux serveur)

Le seul flux serveur = la **re-synchronisation** de la `Review`/`Decision` (AD-8, Job persisté ; 05 §4.5.1 l. 2353-2367 : « une revue **n'exige jamais** le réseau »). `killed` (G-M2) = `Skeleton` + bannière fine DS « Reconnexion… » (05 §3.7 l. 1290-1296 ; ui-libraries §6 l. 185) : le contenu du mirror local s'affiche (AD-7), le composant repasse en état normal quand le resync s'achève (l. 1292-1296). La **création** reste possible en `killed` (écriture locale, pack 03, l. 2355-2357).

### 12.1 Classe offline (catalog) + classe de dégradation AD-1 (master-feature-catalog l. 26)

### 12.2 Miroir local (AD-7 / AD-12) — ce qui **vit** offline

- Le `revues-mois` **fonctionne** offline : les 5 sections sont **lues** du mirror local (PowerSync/SQLite, 03 §4.2) ; la **création** reste possible (écriture locale, pack 03) ; une revue **n'exige jamais** le réseau (05 §4.5.1 l. 2353-2367 : « c'est une **auto-évaluation**, pas une requête de l'agent ») ; le `Pager` (id. 2) **fonctionne** (navigation temporelle locale, l. 746-747) + `Badge` « Offline » (ui-libraries §6 l. 184) ; le `Decision` AD-15 est **saisi** localement (SQLite), sync serveur-wins au retour réseau (productivity/overview l. 54) ; le `Button ghost` « En faire une tâche » (id. 10) **reste actif** (création `Task` locale, AD-7) ; le `Callout warning` « retard » se **calcule** localement (OQ-3, cf. §4a id. 12).

### 12.3 Ce qui **meurt** (killed, G-M2)

- Le **seul** flux serveur = la **re-synchronisation** de la `Review`/`Decision` (AD-8, Job persisté) : le `killed` (G-M2) = le `Skeleton` + bannière fine DS « Reconnexion… » (05 §3.7 l. 1290-1296 ; ui-libraries §6 l. 185) : le contenu **reste** lisible (AD-7), la **création** reste possible (pack 03) ; le composant repasse en état normal **automatiquement** au resync (G-M2 : « sous-état de `loading`, pas un 6ᵉ état canonique »).
- **Au retour du réseau** : les éléments **nouveaux** syncés depuis le cloud apparaissent avec leur `Badge` « nouveau » `primary` (indigo, pas rouge — 05 §3.4 l. 748-750 : le `danger` est réservé à l'échec).

### 12.4 Logo dans les états offline / killed (S9)

- `offline` = le logo **n'apparaît pas** (l'état **est** vivant : la lecture locale **fonctionne**, la création **fonctionne** — pas de marque, pas de signal « coupé » ; la seule occurrence du `Badge` « Offline » = `Badge` `text`, pas un logo).
