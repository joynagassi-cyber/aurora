# progress-dashboard — Progress dashboard (today/week/month/trajectory)

> Module Progress · Route `/progress` (+`/progress/:id`) · SSoT : 05 §4.5.2 (l. 2410-2477) + ADR §18.6 + docs/progress/overview.md (claimé, non détaillé écran-par-écran, OQ-43) · Statut : claimé, non détaillé

## §1 Psychologie designer

- **Objectif utilisateur** : mesurer la **transformation réelle** (pas des compteurs) — répondre aux 5 questions fondamentales de Progress (ADR §18.1) : où en suis-je réellement, qu'est-ce qui s'est réellement amélioré, qu'est-ce qui stagne/régresse, pourquoi cette évolution, quelle prochaine action produit le plus de progrès utile. L'écran est **structuré par question, pas par widget** (AD-14 : « l'analytique est le miroir, pas le tableau de bord »).
- **Contexte** : mobile (Phase 1) ; moment = après une session Focus / une révision QCM / une révison flashcards (le `ProgressEvidence` vient de se produire) ; l'utilisateur revient **en arrière** depuis `/progress` pour vérifier son fil ; réseau = **indifférent** (lecture des miroirs locaux `skill_states` + `progress_snapshots`, AD-7 ; les nouveaux agrégats attendent la connexion, ADR §18.6 + 03 §4.2).
- **Fréquence** : plusieurs fois par semaine (après chaque bloc de travail profond) ; l'écran alimente les **5 lectures** de temps (7 j / 30 j / semestre / année / multi-années, ADR §18.2) — la trajectoire est **primordiale**, le pourcentage isolé est secondaire (règle « Privilégier la trajectoire et les tendances plutôt qu'un pourcentage isolé », ADR §18.2).
- **État émotionnel cible** : **confiance** (les données sont honnêtes, pas de chiffres artificiels ; l'empty state dit « pas encore assez de données »), **clarté** (la structure est par question, pas par widget), **action** (chaque question débouche sur une CTA, pas sur un graphique muet), **calme** (pas de compteur animé, la donnée est vérité pas effet, 05 §2.6 règle 1).
- **Erreur la plus probable** : un agrégat est **incalculable** (donnée manquante sur une période) → `Callout warning` (le bloc est signalé, pas masqué, AD-11 : la fidélité passe par le signalement) ; ou offline → les agrégats **existants** sont consultables, les **nouveaux** calculs sont différés (`Callout info` « les agrégats seront recalculés à la reconnexion », AD-8 : le calcul est un Job persisté).
- **Ce que l'écran RÉSOUT** : 5 `ListItem` dépliables (une par question du ADR §18.1) qui s'ouvrent en **blocs de preuves** (pas d'agrégat isolé : un `Timeline` pour la trajectoire, un `Sparkline` pour la tendance, un `ChartSpec` G2 pour la charge planifiée vs réelle, un `StatTile` pour le taux de réalisation, un `SkillStateBadge` pour la progression par compétence) ; actions flottantes : `Button ghost` « Partager » (export du bloc sélectionné vers `Artifact Hub` §4.6.1, ADR §16) + `Button ghost` « Ajouter au journal » (la décision importante, doc §2.9 : écrit dans `decisions`, module Productivity, pack 01 §4).

## §2 Contexte fonctionnel

- **Entrée** : bloc 4 du Home (`progression critique`, 05 §4.1.2) ; après une session Focus (§4.4.2, le score de concentration alimente l'analytique) ; deep link push « how am I doing ? » (AGT, 02 §6.1) ; **retour arrière** conserve la période sélectionnée (store UI pack 02 §3.2, AD-7 persist).
- **Overlay IonModal `/progress`** (router.tsx detail-over-tab rule 02 §6.1 S1/S3) : le tab courant reste sous l'overlay (pas de navigation destructive).
- **Data** : `ProgressSnapshot`, `ProgressEvidence`, `SkillState` (level, freshness, confidence, evidence, history), `ProgressEvent`, `ProgressTrend` (period aggregate), `Gap`, `TrajectoryScenario` (ADR §18.6 + overview.md §6) ; **lecture** = miroirs locaux (`skill_states`, `progress_snapshots` — 03 §4.2 mirror rule, AD-7) ; **écriture** = pas d'écriture locale (les agrégats sont calculés **côté serveur** par le module Progress, pack 01 §4 : `ProgressTrend`, `ProgressEvent` sont dans PostgreSQL, AD-6) ; les **nouveaux** calculs attendent la connexion (ADR §18.6 : « dashboards read mirrors offline; new scenarios/aggregates wait for connectivity »).
- **Async** : lecture = **locale** (miroirs SQLite, AD-7) → pas de killed ; les **nouveaux** agrégats = flux serveur (jobs persistés, AD-8) → killed possible sur ce flux ; l'écran **n'émet jamais** `ProgressEvidenceCreated` (AD-9/F-07 : seul Progress l'émet, F-07 sole producer rule).
- **Saisie** : pas de saisie (lecture seule, ADR §18.1) ; pas de `TextField` ; le `SegmentedControl` de période (7 j / 30 j / semestre / année) est un **choix exclusif binaire/ternaire** (05 §3.4 : « le mode est persisté par l'écran (store UI pack 02 §3.2) ») — pas un `Select` (le choix est **exclusif** et **binaire/ternaire**, le `SegmentedControl` est justifié ici, §3.4).
- **Sortie** : vers `fiches-liste` (§4.7.1, « réviser la compétence signalée ») ; vers `progress-dashboard` (lui-même, pas de redirection) ; le contenu **partiel** apparaît dès que les premiers blocs de preuves sont prêts (pack 02 §7 : « le content doit se montrer partiellement en dessous »).

## §6 Tokens (discipline AD-17, 05 §2 l.93–346 + ui-libraries S4 l.145–160)

- **Aucune valeur brute** : pas de hex, pas de px de spacing/typo/radius codé en dur — toujours via variables CSS `hsl(var(--aurora-*))` (05 §5.2/5.3, ssootCode tokenRefs aurora.css).
- **Règle bloquante 05 §5.1 (l. 2931)** : le thème ne touche **jamais** success/warning/danger/info (frozen semantic tokens) — utiliser uniquement via les variables, pas de redefinition par thème ; les `StatTiles` (le taux de réalisation, le delta `success`/`danger` texte) sont **frozen** (05 §3.3 l. 609-610 : « le delta en success/danger texte, jamais une flèche seule — le texte dit la direction, l'icône ne fait pas le sens, a11y §6 »).
- **10 thèmes + 3 presets = comportement par couche** (05 §5.2, ssootCode themeRefs) : pas de valeur par thème (jamais d'override par thème sauf L3 local override = Focus only, OQ-15) ; l'écran ne code **aucune** valeur par thème ; le `SkillStateBadge` (maîtrisé=success, fragile=warning, oublié=danger, intermédiaires=neutral) est **frozen** (05 §3.6.11 l. 1134-1155 : « le badge n'affiche que 3 familles de couleur (règle §3.6.6 des 3 couleurs fortes) »).
- **focus visible** : le theme owns focus-ring (aurora.json focusTreatment = ring, ssootCode a11yRefs) — pas de gestion manuelle du focus par écran ; tous les `icon buttons` portent un `aria-label` (a11y §6, 05 §6.3 l. 3308-3346).
- **icônes** : 05 §2.5 (l. 287) — lucide (ssootCode paginationRefs Chevrons/MoreHorizontal) ; **pas** de custom SVG decoration (S3 l. 141 interdit, ssootCode forbidden).
- **coins** : radius ≤ 8px (S3 l. 142 interdit > 8px) ; **élévations** = 05 §2.4 (l. 254), pas de box-shadow brut.
- **`ProgressBar`** : toujours déterminée (le temps est connu, 05 §3.3 l. 560-570) — **jamais** `indeterminate` (le glissement = uniquement pour un chargement **réellement** indéterminé, 05 §3.3 l. 562-563) ; le `ProgressRing` = le temps restant ou un pourcent circulaire (05 §3.3 l. 572-588) — **pas** de ring de quota (le quota AI est un backend concept, AD-4/AD-5 : « un ring de quota n'existe pas dans l'UI V1, règle §12 'simple en surface' », 05 §3.3 l. 575-576).
- **`SkillStateBadge`** : **pas** de `loading` (c'est une projection d'un `SkillState` AD-15, qui est **connu** dès qu'il existe, 05 §3.6.11 l. 1148-1151 : « le badge n'a pas de loading (c'est une projection d'un SkillState AD-15, qui est connu dès qu'il existe) »).
